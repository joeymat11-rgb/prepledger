## The actual ownership boundary

The unchanged Node test invocation uses process isolation by default ([runner.js:537](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/test_runner/runner.js#L537)). It launches the test file through child_process.spawn with pipe stdio; only watch mode adds IPC ([runner.js:361](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/test_runner/runner.js#L361)). Thus the test-file owner is a separate OS process beneath the outer test runner, not a worker_threads.Worker. Its exit code and stdout completion participate in the outer result ([runner.js:435](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/test_runner/runner.js#L435)). Any stable state proposal must cross both existing process boundaries without changing this command or ownership.

## Native V8 call coverage

There is a real smaller builtin to investigate. NODE_V8_COVERAGE propagates to subprocesses ([CLI documentation](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/doc/api/cli.md#L3681)); pre-execution sets the coverage directory and source-map getter; native startup enables detailed precise call counts and registers an AtExit callback ([inspector_profiler.cc:368](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L368), [startup:448](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L448)). This avoids the specific application-resource tagging performed by the rejected async observer. Avoiding that mechanism is not yet a proof of noninterference or complete observation.

Normal SpinEventLoop drains tasks and beforeExit work, then emits exit ([embed_helpers.cc:22](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/api/embed_helpers.cc#L22)). FreeEnvironment disables ordinary JS calls, stops subworkers, runs cleanup, then AtExit ([environment.cc:504](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/api/environment.cc#L504)); worker environments also have their own loop and teardown ([node_worker.cc:299](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/node_worker.cc#L299)). These support late normal collection, not an unconditional last-observation theorem.

The inspected implementation leaves these precise gaps:

- Collection is a snapshot, not a continuing terminal record. Profiler.takePreciseCoverage calls CollectPrecise ([V8 profiler:411](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/deps/v8/src/inspector/v8-profiler-agent-impl.cc#L411)); precise collection reads then clears invocation counts ([debug-coverage.cc:501](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/deps/v8/src/debug/debug-coverage.cc#L501)). Public v8.takeCoverage can request another snapshot; v8.stopCoverage disables collection ([v8 documentation:540](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/doc/api/v8.md#L540)). Treating one later-found file as the complete cumulative history is unsupported.
- The internal ending_ latch is not written as a terminal flag. End sets it before TakeCoverage and does nothing on a later End; filenames contain PID, milliseconds and environment thread ID, not finality or a complete snapshot sequence ([inspector_profiler.cc:208](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L208), [End:382](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L382)). An earlier successfully written file can remain if the final request or output fails; a sole file is not sufficient evidence that no earlier request existed.
- Directory, response parsing and output failures print/return rather than certify a different child exit result ([response:176](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L176), [directory:191](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L191), [WriteResult:74](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L74)). Stderr is another output channel, not guaranteed durable knowledge under the stated later-IO failure rule.
- After obtaining the profile, WriteProfile explicitly allows JS to call the source-map-cache getter; getter failure discards output ([inspector_profiler.cc:257](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/inspector_profiler.cc#L257)). The getter iterates cached module-associated records ([source_map_cache.js:339](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/source_map/source_map_cache.js#L339)); its iterator reads moduleInstance[source_map_data_private_symbol] after dereferencing a module ([source_map_cache_map.js:91](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/source_map/source_map_cache_map.js#L91)). Further application-observable work through this route is an unresolved reachability/noninterference question, not an executed witness. The source comment against user code is not a proof that all such property access is inert.
- ReallyExit calls RunAtExit before converting its argument with Int32Value ([node_process_methods.cc:492](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/node_process_methods.cc#L492)). Ordinary process.exit passes a normalized exit code ([per_thread.js:233](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/process/per_thread.js#L233)); nonprimitive reachability through the direct binding is not established here. This is a specific unresolved post-snapshot coercion route, not a demonstrated original-child failure.

Preliminary classification: the blanket assertion that a found native coverage file proves all relevant JS finished is refuted by snapshot/output semantics. Whether a carefully constrained capture protocol can close those gaps while retaining every existing bar is unresolved. At most a source-targeted public experiment could answer the remaining reachability facts; this note grants no such execution and no implementation.

## Stable atomic state

Worker-thread SharedArrayBuffer sharing is a real builtin within one process ([worker documentation](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/doc/api/worker_threads.md#L12)). Its message serializer stores shared_ptr<BackingStore> and the receiving isolate constructs a SharedArrayBuffer on that backing store ([node_messaging.cc:356](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/node_messaging.cc#L356), [receiver:191](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/node_messaging.cc#L191), [storage:116](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/node_messaging.h#L116)). This describes same-process backing-store custody, not an OS mapping attached to the original test-file process.

Advanced child-process IPC serializes a length-prefixed byte stream through fresh DefaultSerializer/DefaultDeserializer instances ([serialization.js:97](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/lib/internal/child_process/serialization.js#L97)). The V8 serialization API's shared-buffer ID requires an out-of-band mechanism and an already supplied backing buffer; the ID does not create one ([v8 documentation:814](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/doc/api/v8.md#L814), [node_serdes.cc:123](https://github.com/nodejs/node/blob/aa4c77582be995286fc6e00aaf530dc7ade102a9/src/node_serdes.cc#L123)). The original runner does not even configure this IPC channel for the test file. Replacing process isolation with a Worker or --experimental-test-isolation=none changes the contract.

Preliminary classification: claiming that worker_threads or V8 serialization alone supplies the required cross-process atomic mapping is refuted. A stable mapping approach itself remains unresolved, not impossible. It needs a named, reviewable primitive and a proof of attachment across the unchanged process tree, state lifetime through actual termination, atomic publication/failure behavior and noninterference. No native binding has been researched or installed. A same-process observer worker would still need to export surviving knowledge before its entire process terminates.

No extra alternative is proposed. The smallest useful next work is to resolve a specific terminal-coverage fact or name the missing cross-process mapping primitive, before authorizing another capture implementation. A change from guaranteed refusal/noninterference to best effort would be a bar change for PM/owner disposition; this assessment neither proposes nor assumes it.
