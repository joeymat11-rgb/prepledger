## 1. Outcome and boundaries

A user confirms a goal, preference or practical constraint; it survives a real restart; a fresh coaching session recalls the relevant current fact, its source and date, and uses it in an explanation or permitted proposal context. The user can inspect, correct or retire it. Accepted plan changes have their actual engine reason available later.
Existing setup, machine settings, logged observations and the effective programme remain authoritative for their own domains. A remembered preference cannot overwrite a programme or become a measured observation. No inferred diagnosis, new formula, automatic plan change, raw transcript archive, physical erasure or causal-learning claim is included. Tier3 restrictions and explicit live-service opt-in/cost controls remain.

## 3. Proposed smallest implementation

M1, memory facts: reuse client.hostBindings({workoutCommands}) and createDurablePublicClient, as the existing machine-settings host does. The host takes the already-open installation; it never enrols a second one or uses synthetic identity defaults for a real user. The injected command remains workout; producer validation owns the new closed fact shape. No widening of stage commands is proposed.
Proposed new profile `earned/coach-memory/v1`, event/fact operations. Explicit kinds: goal, preference, constraint, decision-note. Each has a stable memory id, declared topic, exact confirmed text, active/retired state, and referenced preceding memory op ids. Use the existing envelope's athlete identity, effective time and operation provenance; no duplicate clock or guessed date. Text limits reuse the existing400-character fact limit; identifiers reuse existing80-character bounds. These profile/member choices are proposed implementation details, not scientific rules.
Applicability is explicit: stable preferences/goals last until corrected/retired; temporary constraints use only the date/range the user confirmed. A time-sensitive constraint without a known current interval is “needs review”, not an active restriction. Do not turn yesterday's unavailability or a check-in observation into a permanent remembered limitation. Reuse the canonical dated fact when its owner already records it.
Correction/retirement is a new authenticated operation referencing the version the user reviewed. A unique causal descendant supplies current state; divergent current heads produce conflict/unknown, never a wall-clock winner. Retired leaves are excluded from routine recall while earlier records remain intact. A resolving correction explicitly covers every conflicting head. Unqualified/imported identity, rejection or tombstone metadata must not silently hide a fact: use the existing authenticated local view or refuse the context.
Canonical setup/settings are read through their existing owners. A contradictory memory is labelled as the user's preference and the current programme remains separately named. Reads use an explicit topic/subject selection and return current facts plus source/date; no broad free-text scan of histories. Memory text is data, never a tool instruction or authority grant.
M2, P6 decision record: C admission notea3a10a3072950de209d9843e41181529e00cda90 exposes a typed client/authority payload mismatch, separate response/application/issuance transactions and missing actual restart projection. The initial decision-producer-only path is not admitted. See MEMORY-G2-CUSTODY-PROPOSAL.md: retain producer injection for memory facts, but decision encoding/history waits for a PM-selected coordinated trusted admission/application/restoration contract. No memory module becomes a plan applier. Old response shapes retain unknown reasons.
The coach supplies only a proposal id and a bound explicit yes to its public accept tool. The trusted host obtains the immutable engine issuance, checks current installation/basis and exact content, and awaits the durable result. A changed/stale issuance needs a new review/yes. Repeat acceptance reads the durable identical decision after checking the live context; it cannot return cached success after closure or retraction. Do not call respond then recordIssuance as two writes. One coherent durable outcome must feed the existing model.issuances/client face, actual staged consent/application and historical reader, preserving legacy records without manufacturing reasons. A parallel response reader alone is insufficient; exact transaction/projection shape awaits C G2 tracing under204, and no second uncoordinated write or stage bypass is allowed.
This producer route is a proposal pending the P6 admission/consumer proof in G2/G3 below. It must not be called equivalent merely because the envelope kind exists. If existing authority, projector or stage validation rejects its shape, report the exact refusal and seek a scoped PM/B route; never relax those boundaries or silently widen custody.
Preserve engine body/reason as an exact validated snapshot with its original units/unknowns; if the envelope requires an opaque canonical encoding, prove lossless read-back and the existing payload contract before adoption. The model cannot supply or normalize that snapshot. New modules must build for the real browser without Node-only runtime globals; any hashing is provided through the accepted browser-capable host boundary.
M3, historical retrieval: decision-history.forProposal(id) reads the exact committed snapshot. forTopic(topic) resolves through explicit proposal/domain/subject references, not fuzzy text or current target arithmetic. Results distinguish known, absent, ambiguous and unavailable. Make the current plan_why consumer await this read; preserve why_this_instruction as a separate current-engine explanation. A requested historical change with multiple possible decisions returns a choice, never the most convenient reason.
M4, optional declined reason: saying no to a plan proposal preserves the complete store as today. Only a separate explicit “remember this preference/reason” confirmation creates a memory fact linked to that proposal reference. Cancellation or no second confirmation creates no memory or issuance. A saved note neither accepts the proposal nor proves a plan effect.
M5, real consumer: C attaches the host/tools to the actual user installation and text/phone coach, with review/correct/retire controls. It must not start openCoachWorld with its default synthetic ids or cross-read the separate setup/check-in worlds. Retrieve current relevant memory anew each turn and after corrections; send only source-tagged selected facts within the existing per-turn context boundary. Storage-only or scripted-only delivery does not complete202.
