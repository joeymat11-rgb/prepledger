## 1. Problem, evidence and selected approach

Current `bridge.cjs:executeR1` loads/decrypts every own-account row on every page; `project.cjs:project` constructs the complete duplicated claims/log/retained-row payload before `http.cjs` cuts a page. `verify.cjs:assemble` joins the complete payload and repeats the projection. Population scoping and owned buffers did not meet the original96MiB resource limit. The single retained heap diagnostic found no concrete improper retainer. Repeating that experiment or lowering the complete-history cap is not the next action.

Select a separately versioned, revision-pinned **raw inventory transport**, staged durably by the existing recovery client and validated completely before use. The server's new page signature attests exact scoped stored bytes and snapshot continuity; it does **not** claim that those bytes already passed all R1 semantic checks. The final consumer must prove every existing profile/claim/signature condition before awarding complete recovery. This explicit change of validation location requires review; counts or a signed page alone cannot replace that gate. Do not call the existing `project` on every page or add a second accepted-data store.

Independent130 accepted v0.1 **as a proposal and probe only**, not adoption/build readiness. Its five corrections are incorporated here. Tracked `test/r1-paging-probe.test.cjs` now passes8 cases (9 Node tests including the parent): exact inventory larger than1MiB, real32-row and262,144-byte boundaries, a400,000-character value, a1,200,010-byte key, UTF-8 binary/NFD/NUL/raw JSON preservation, scope/replay/revision/control cuts, concurrent other-athlete write with fresh retry, and a dropped-standing-event redundancy witness. Its generic large history rows are **not a valid complete R1 cross-record account**. The separately declared standing-event witness is relationally valid but does not claim the writer emits duplicate genesis events. No real HTTP, complete staged-profile, memory, phone or private-ledger acceptance is inferred.

## 2. Database read and snapshot boundary

Use the existing `authority_rows` table, P1 codec, subject binding, global revision and storage-control guard. No new plaintext table, snapshot copy, key registry or server cache. Initial authenticated issuer/subject/origin plus enrolled actor determine scope; never accept an athlete ID as authority. Freeze the exact20 profile collection names from `project.cjs`. In the first consistent D1 batch read revision, subject binding, current actor standing dependencies, storage control, per-collection row counts and the first page. Unknown collections fail; zero-count collections are explicit. Counts are a completeness cross-check, never the proof by themselves.

On every page, one consistent batch reloads revision, subject binding, current actor standing dependencies, storage control and that page. The standing dependency set must implement the existing registry/device/lease/revocation decisions exactly; it is not merely a cached account-active flag. Pin its indexed row selection in code/tests before releasing the route. A replacement binding, account closure, device revocation or invalid standing cannot reuse earlier authorization. Preserve the existing authenticated negative-ingress and state precedence rather than inventing a new lease permission.

Select rows strictly after `(collection,row_id)` using SQLite BINARY order and the existing athlete/collection/row_id key. The probe limits the candidate window to32 key/length tuples, then selects its longest prefix within262,144 physical column bytes; if the first row alone exceeds that budget, return that single whole row. Physical budget includes UTF-8 athlete/collection/row_id/value/sealed lengths plus8 bytes for storage_revision. Never split/drop a row silently, use locale sorting or advance a cursor over an omitted row. Page SQL, bound parameters and caller-derived scope need adversarial inspection, not only the probe's helper assertions.

Decrypt only selected rows and the fixed standing dependencies with the existing P1 codec. After validation, use the existing failing revision/control constraint as the linearization cut; stale work returns a typed restart, never a signed successful page. This new read path must **not increment** the global revision itself. Existing write paths and old read-route semantics stay unchanged. A successful final guard proves a snapshot at that cut, not freshness forever; K1/currentness and the local activation fence still apply.

Any global write during the attempt invalidates its snapshot. Retry from a new manifest; never stitch generations. This may cause starvation during sustained writes, including another athlete's writes or old reconciliation reads. Keep attempts bounded under the existing retry policy and report incomplete recovery; do not suppress other devices' legitimate writes or waive the revision. Demonstrate practical completion with the supported two-person workload **while the other athlete writes concurrently**, not merely before or after recovery, before private activation. The tracked probe overlaps an actual second-athlete P1 write with a suspended first-athlete page, verifies refusal and complete fresh retry; this is not the real two-person HTTP/phone throughput gate. No per-athlete revision redesign is included.

## 3. Proposed wire boundary and exact-byte identity

Use separate `POST /reconcile/rows` and domains `earned/r1/rows-v3/{manifest,page,cursor,finish}`. No fallback interpreting these as existing `earned/r1/*` payloads. Use existing pinned public P-256 encoding and canonical signing machinery; generated test keys only. The corresponding codecs/closed ordered field lists and canonical/signature vectors must be committed with implementation, not inferred by W6 from prose. Old enrollment, renewal and replay results stay on their existing domains and contracts.

| Exchange | Bound content and required interpretation |
|---|---|
| Begin | Existing authenticated caller and locally retained reconciliation request; bind its nonce, context ID, request/basis digest, **claim_set_digest**, mode and derived scope digest. Compute the claim digest with domain `earned/r1/rows-v3/claims` over UTF-8 `JSON.stringify` of the validated, ordered claim array, preserving its original envelope-base64 fields and key/array ordering; retain the full request digest separately. Manifest signs those bindings, source revision, storage-control fingerprint, random snapshot ID,20 ordered collection counts, starting empty cursor/chain and profile version. It contains no health payload or signing secret. |
| Page | Request carries `profile,device_id,manifest,cursor`. The device selector is required to call the existing issuer standing check on each stateless request; it is never authority. Recompute the signed scope from the authenticated issuer/subject/origin, current database athlete binding and this enrolled actor before returning a page. A different same-account device also cannot reuse the cursor. The manifest and previous **signed cursor certificate** still bind caller/session/context. Response signs manifest digest, ordinal, previous certificate digest, exact encoded row-batch digest, resulting chain digest, cumulative20-count vector and next cursor certificate digest. Rows carry collection enum, exact UTF-8 row-ID base64url and exact original logical-value base64url. Ciphertext/seal/storage keys do not travel as recovered facts. |
| Cursor | Separately signed small-in-row-count certificate binds the manifest, ordinal, last exact binary key, cumulative counts and chain digest. It contains no row values. Reject cursor substitution, bad signature, mismatch, overflow, unknown collection, invalid/noncanonical base64 or invalid UTF-8 before querying. Replaying the same cursor at the same snapshot returns the same row identities/bytes and chain, even if the signature encoding itself is nondeterministic. |
| Finish | Only an actual empty next-row query at the same revision/control/standing cut, with cumulative counts exactly matching the manifest, permits a signed finish marker. **This attestation of the exhausted scoped query is the completeness proof; the20-count vector is redundancy.** Bind the entire chain, counts, source revision and current context. No page count, timeout, filled budget or empty client buffer implies completion. Finish means complete scoped inventory delivered, not admission, outbox drain or recovery activation. |

Hash every exact bounded encoded row batch; chain with a domain-separated hash of the preceding chain digest, manifest digest, ordinal, batch digest and cumulative counts. Fixed hash inputs and integer encodings are pinned vectors. A cursor-reference digest covers its closed ordered record **excluding only authority_signature**, under `earned/r1/rows-v3/cursor-reference`; the full signature must still verify before that reference is trusted. Valid P-256 re-signing can change signature bytes, so references and duplicate checks must not falsely call it a conflicting cursor. Compare manifest/ordinal/original row bytes/chain/cumulative counts and semantic cursor contents; reject any actual difference. The tracked frame test re-signs a cursor and verifies its reference remains equal. This avoids WebCrypto needing an incremental whole-history digest. Preserve source strings and row keys exactly; do not JSON-reserialize a stored original, normalize Unicode or reuse the operation's canonical HMAC as an exact-byte hash. Operation IDs, commitments, dispositions, original signed envelopes and receipt meaning are unchanged.

Responses use `{manifest,page}` or, only on the terminal empty-page cut, `{manifest,page,finish}`. The first page has ordinal1, preceding counts all zero, preceding chain=manifest.chain_seed and previous_cursor_digest=the domain-separated `earned/r1/rows-v3/cursor-seed` hash of the manifest digest. All positional `cumulative_counts` vectors follow the exact frozen `project.cjs:COLLECTIONS` order, from metadata through standingEvents; manifests enumerate names in that same order. Later requests carry the previous verified signed cursor. A continuation cannot select its own ordinal, count vector or last key outside that certificate.

An empty page has `rows:[]`, unchanged cumulative counts, next ordinal and the normal hash of that empty batch. Its next cursor retains the preceding cursor's `last_key`; if no row has ever been delivered, `last_key:null` and all counts are zero. Null is never an empty string or a fabricated key. An empty page requires the signed finish from the same exhausted-query/standing/revision cut; without it recovery is incomplete. A finish on a nonempty page is invalid. An initially empty inventory is representable, but full profile/standing validation still rejects missing required account records; no empty first-use is inferred. The manifest/page/optional-finish wrapper overhead is included in the fixed metadata bound; no separate unbounded bootstrap wrapper is assumed.

The raw row key is not universally a128-character operation identifier: current storage accepts other nonempty UTF-8 strings. The probe includes a control-character key. Encode arbitrary keys as base64url rather than assuming JSON escaping is bounded by their original byte length. The SQL budget limits result column bytes, **not total Worker allocation**, SQL engine work, wire buffers or standing dependencies.

## 4. Finite per-request limits, without a total-history cut

Cloudflare documents a maximum string/BLOB/table row of **2,000,000 decimal bytes**, not2MiB, and a30-second batch deadline. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/). Batches execute transactionally and fail as a unit. [D1 batch API](https://developers.cloudflare.com/d1/worker-api/d1-database/). These vendor constraints do not establish the application's96MiB memory gate.

`test/r1-paging-wire-bounds.test.cjs` now pins a concrete proposed frame encoding and proves its size relation, using actual P1 sealing/opening and generated P-256/public verification. It tests32 ordinary rows and near-limit ASCII/NUL/UTF-8 keys and values, exact byte roundtrip, domain separation, maximum signature epoch length, safe-integer20-count vectors and claim substitution/order. The large-key frames actually exceed1MiB; merely rejecting them is not a complete-history optimization. The frame-size test is constructed evidence, **not D1 maximum-row/memory acceptance**. `paged-codec.cjs` now implements closed duplicate-safe parsing, generated-key public signature verification, exact count/chain/cursor/finish and caller-context binding. `paged-bridge.cjs` and the separately named Worker route now implement the real six-statement P1 path. Full durable staging/profile/resource qualification remains open.

Let P=2,000,000 and N=32. In the current P1 format, original value bytes are no longer than the stored encrypted envelope; thus the selected sum of raw key+value bytes is at most the physical selection bound P (ordinary pages have the smaller262,144 bound). Unpadded base64url length is at most4×ceil(bytes/3). The first4×ceil(P/3) term covers **key+value jointly in the row batch**; the second covers the **same final key repeated in next_cursor.last_key**, not a second full-sized value. Allow8N bytes for separately encoding the row fields, and M=8,192 for fixed metadata, including collection names, safe-integer counts, digests, maximum157-character signatures and nested certificates. The longest-collection/maximum-count frame overhead is tested below M. Independent132 accepted the earlier cursor-only request bound2,674,860 and response bound5,341,784. Implementation then exposed a missing actor selector: the opaque scope digest cannot identify the device for the server standing check. Add the required `device_id`, whose canonical encoded JSON is bounded by the existing1,048,576-byte begin body. The revised continuation bound is4×ceil(P/3)+M+1,048,576 = **3,723,436**; page <=8×ceil(P/3)+8N+M = **5,341,784**. New-route ceilings are therefore4,000,000/6,000,000; begin remains1,048,576 and all old routes keep their limits. This extra actor/size correction awaits independent implementation review;132 did not approve it. It does not change the96MiB resource gate or impose a history cut. These are bounds for **this exact encoding**, not arbitrary JSON shapes. Any extra variable field requires re-derivation. The production closed decoder must reject unknown/duplicate fields and enforce all primitive/collection/key/signature/counter bounds before deployment acceptance.

The tracked constructed frames fix manifest fields to profile/key_epoch/scope_digest/nonce/context_id/request_digest/basis_digest/claim_set_digest/mode/revision/storage_control_digest/snapshot_id/collection_counts/chain_seed/signature; cursor fields to profile/key_epoch/manifest_digest/index/last_key/cumulative_counts/chain_digest/signature; and page fields to profile/key_epoch/manifest_digest/index/previous_cursor_digest/rows_digest/chain_digest/cumulative_counts/next_cursor_digest/rows/next_cursor/signature. Finish fields are profile/key_epoch/manifest_digest/final_cursor_digest/chain_digest/cumulative_counts/revision/storage_control_digest/context_id/scope_digest/nonce/claim_set_digest/signature; it is also signed/verified and bounded below M in the tracked evidence. `signature` here denotes the existing `authority_signature` field, not a second format. Continuation carries only profile/device_id/manifest/cursor, not the original claim bodies again. Begin has closed fields profile/device_id/request/basis_digest; `request` uses the existing validated request schema. Every hash uses the existing43-character SHA-256 base64url representation. Begin retains the existing bounded claim/request contract; pagination never weakens it. These field lists and validation-location mapping permit a focused implementation after amendment acceptance; production acceptance still requires the implemented closed decoder, signed-finish/omission tests and complete staged verifier, not another preliminary framework.

There is no new complete-history byte/page ceiling. The finite database, available device storage, safe integer counters, existing retry/deadline policy and measured supported-device limits still bound the operation. Exceeding a real supported capacity produces explicit incomplete recovery, retains original data/outbox and blocks activation; it never truncates to recent workouts. Do not advertise unlimited capacity. Owner-history fit is a later private verdict under existing custody, never a public fixture or count.

## 5. Durable staging and complete interpretation

Stage each verified page and its receipt/cursor atomically in the existing recovery repository, associated with snapshot/context and an inactive generation. A durable page says only recovery progress. Never expose partially recovered truth, advance the active frontier, drain an outbox or replace the current generation. Reject conflicting duplicates; identical retries are idempotent. Persist original logical row bytes, not a second independently writable domain ledger. A restart may resume only after re-proving the same snapshot and current standing; changed source/context abandons that candidate while preserving the existing active data.

Before activation, a bounded indexed validation pass over the staged rows must perform **all** conditions currently expressed by `project.cjs:validateRetained/scopeCheck/claimsAgainst/payloadState` and `verify.cjs:assemble/originalRecord/lease`, including collection closure, unique identities, contiguous accepted1..W, exact operation/log relations, history cardinality/status transitions, device/lease/slot/ownership/standing relations, issuance origins and the exact disposition/lease public signatures. Recompute **only the manifest-bound claim set**, first matching its digest and the original request; preserve CURRENT_DEVICE foreign-device claim refusal. A transport summary or counts-only check cannot stand in. Rejected/WAITING facts and original envelope mismatches keep their existing meaning. The tracked dropped-extra-standing-event witness passes the old relational validator both before and after omission but changes the source count vector, demonstrating why neither relational validation nor client-visible rows can independently prove completeness. The real signed-finish omission mutation is still required on the actual transport.

The validation-location mapping from independent130 is binding for the implementation: relational `validateRetained`, scoped `claimsAgainst` and the relational portion of `payloadState` may run once over the complete staged original rows; per-lease/per-history public signatures remain mandatory in the consumer. Five proofs **stay server-side**: authenticated principal-to-athlete binding, revision/storage-control linearization, live per-page actor standing, exhausted scoped-query completeness, and exact-byte attestation of stored originals. A client signature check authenticates these attestations; it cannot independently reconstruct those server facts or substitute snapshot-era standing for live standing. Do not move any of these five checks to the final consumer.

Implement those passes through staged-store indexed reads/bounded caches, without collecting every payload into a new giant `JSON.stringify` or calling the old capped projector. Compare the new logical result with the old accepted verifier on every supported under-cap corpus and negative vector; add valid larger accounts to prove the new route is not only a generic byte export. The new inventory verifier may never return the old full-payload proof type. Preserve raw originals for subsequent actual port/workout interpretation. Source semantic invariants are copied/mapped, not silently relaxed to enable streaming.

Final activation still uses the existing local revision/token, independently known standing/knowledge-loss fence, authenticated final source observation, original local claims/outbox reconciliation and atomic generation switch. New writes or relevant learned facts invalidate a stale candidate. None of this creates current-safety permission, an issuer, a new lease, qualified prescription, or a recovery of unavailable keys. Known standing17, integrity/failed durable fence18, authenticated rejection handling19 and clock20 retain their accepted mappings.
