# W6 Clerk ingress — bounded primary-source research

2026-09-06, 09:04–09:07 UTC. Read-only research; no SDK installation, app modification, account activity, real credentials, private records or executable provider test. W6 claim remains held. This note is a technical proposal, not independent acceptance or a product-rule exception.

**Finding: `polling:false` plus `touchSession:false` does not establish a quiet Clerk JS runtime.** Current documentation scopes those switches narrowly; a pinned source tree contains independent token timers, focus/visibility refresh and cross-tab ingress. Removing our subscriber with `off()` does not stop internal observations or prove queued callbacks cannot run. Therefore it cannot be the K1 CLEAN/closed-ingress proof.

## Feasible minimum controlled candidate

**Direct Clerk Frontend REST requests are explicitly supported for browsers**, per the [API overview](https://clerk.com/docs/reference/api/overview). The [architecture guide](https://clerk.com/docs/guides/how-clerk-works/overview#the-frontend-api) also permits complete flows on FAPI, while warning that FAPI has substantial client-side complexity and recommending SDKs for normal integrations. This is an available option, not a free shortcut or an accepted design.

Pinned public OpenAPI repository **7987d1b776258d5ddd9163e1a03d256b5ac4d64a**, latest listed FAPI spec [2026-05-12.yml](https://github.com/clerk/openapi-specs/blob/7987d1b776258d5ddd9163e1a03d256b5ac4d64a/fapi/2026-05-12.yml). It explicitly describes:

- 1206: `POST /v1/client/sign_ins`, with email_code plus identifier.
- 1381 and1485: prepare/attempt first factor; email-code preparation sends the code and attempt takes it.
- 2572: `POST /v1/client/sessions/{session_id}/tokens` creates a session JWT.
- 2478: `POST /v1/client/sessions/{session_id}/end` ends that session.
- 8693–8701: production browser authentication is the `__client` cookie. It is not a browser-held Clerk secret key. Development authentication differs; do not transplant its query-token mechanism into production.

Minimum candidate for independent review: **do not load Clerk JS in the enrolled offline Today execution context**; own a narrow native-fetch adapter for the ruled email-code sign-in and explicit token acquisition/ending. Every request, response parsing/verification and deliberate session action belongs to a durably armed K1 observation. No periodic refresh, focus listener, background sync or Clerk BroadcastChannel is introduced by this adapter. Acquire a fresh token when sync needs it; token/session expiry itself remains state11 where the existing lease/budget permits logging.
This containment is an architectural inference: without importing SDK code its timers/listeners are absent, but the proposed adapter is not implemented or proven. It must not ignore previously learned revocation/rejection. A browser cookie changed externally is not by itself authenticated product standing; the next controlled response must be processed correctly. Actual application account-switch/signout and cross-tab coordination remain owned K1 channels, not eliminated by choosing REST.
Sign-out still needs the actual pre-armed UI intent cut; sending session-end later does not retroactively preserve intent. Every aborted/ambiguous request retains its obligation. Request cancellation alone is not a safe-close barrier; do not discard a response already learned. This proposal does not change late-creation,24h/64, coherent restore or failed-knowledge rules.

## Unknowns to close before adoption

1. Exact production FAPI request headers/versioning, cookies, CORS/CSRF and same-site/domain behavior; sign-in completion/token handoff/session tasks. The OpenAPI routes alone are insufficient implementation instructions.
2. Email enrollment versus sign-in, failure/rate-limit/retry behavior, CAPTCHA/Protect or required challenges and their own event/request lifecycle. No assumption that the owner's configured account allows challenge-free custom flows.
3. How a production JWT satisfies W5's pinned issuer/audience/origin and enrolled-device requirements. Clerk authentication does not replace W5 standing/lease reconciliation.
4. Signout and account switch across the actual supported PWA/tab topology, queued events after completion, browser-cookie updates, and absent versus independently lost standing. No complete close protocol is granted here.
5. Whether a narrower SDK lifecycle boundary exists with a documented cancel/drain guarantee; none is established by polling/touch/off. Do not patch SDK internals, monkeypatch global timers/fetch/BroadcastChannel, or misdeclare an ordinary Safari PWA as a nonstandard/headless browser to manufacture quietness.
6. Physical installed Safari behavior, production cookie persistence and recovery. Local synthetic success cannot substitute for these later gates.
