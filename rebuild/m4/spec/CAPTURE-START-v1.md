# Original workout prescription in Start — proposed contract v1.1

ASTRA; September9. Executes BRIEF-OWNER-WORKOUT §1 prescription capture/resume and §2 actual projection. Technical proposal, not an issued schema, implemented command or accepted private release. Actual inspected inputs: R1 `60e073bb4c77d87c7179971d8f77e20655f5805b` (P1 component accepted in Opus102/104), W6 `17fa69f09a19e0b6a72566c9504fddebdd599a0b` (bounded component accepted in Opus96), shared basic shape and full PRODUCT-GOAL v3. Prior detached CAPTURE-JOIN01 preparation is not adopted.

## 1. Decision and invariants

Put the immutable capture **inside the existing session-start envelope**, as one new kind-specific field `prescription_capture`; keep `payload:{}`. Build it through the ONE actual `Ops.build(...extra...)`, before its existing `earned/op/v1` commitment. Start identity already binds athlete, originating device, sequence, lease, schema, split slot and plan basis; do not duplicate those as a competing identity inside the capture. The whole Start and outbox entry commit in the existing one W6 generation. Existing `operations` and `log` rows carry it remotely; P1 encrypts their complete original values, and signed recovery carries their original bytes. No new collection, detached-object upload, capture key, encryption envelope, HMAC domain or issuer registry is needed for this representation.

This is an amendment to the **unissued** complete schema2 proposal, not permission to reinterpret an issued schema or enable production issuance. The amended captured-workout profile requires this field on every newly created Start; it is not an optional way to skip capture. Current basic-only validators/commands reject the extra field; that rejection is correct until the amended manifest, shared validator, command/admission/reference binding and capability transition are implemented and reviewed. Existing schema1 and immutable historical Starts stay byte-identical. Existing component-only schema2 fixtures are not evidence of a production schema rollout.

The record means “these were the original instructions displayed for this Start.” A valid operation commitment or authority receipt is not proof that those instructions were scientifically correct, current, consented or safe to perform. The qualified producer and existing basis/permission gates must establish those properties. Neither this field nor a caller's `verified:true` can grant them. Reopening reads the captured record; it never rebuilds the original instruction from today's engine state.

Byte-exactness is the **storage and authenticated raw-byte recovery** guarantee. The unchanged operation canonicalizers NFC-normalize string values (`client/canonical.cjs:87` at W6 pin; `authority/canonical.cjs:27` at R1 pin), including `label`, `display` and the contents of `source_json`. Thus the operation commitment binds their **NFC equivalence class**, not every original UTF-8 spelling. NFD/NFC-equivalent captures can share one valid commitment. Do not normalize stored original strings, change the canonical/HMAC domain, or claim that commitment alone detects this difference; the P1/raw-recovery byte checks must detect changed original bytes. Key order, decimal spelling and escapes inside `source_json` remain literal ASCII distinctions. Opus108 permitted implementation subject to this correction and the existing gates.

## 2. Exact proposed wire shape

`prescription_capture` is an own enumerable JSON data object with exactly `profile, producer, basis, session, slots`, in any property order under the unchanged canonical contract. Profile is `earned/workout-prescription/v1`. Reject accessors, symbols, hidden extras, custom prototypes, cycles, sparse/extended arrays, undefined/nonfinite values and malformed strings without invoking getters, using the existing shared descriptor-safe JSON ingress discipline. No defaults, trimming, scalar/vector flattening or implicit coercion.

| Field | Exact representation and meaning |
|---|---|
| `producer` | Exactly `{app_build, engine_build, rule_profile, source_schema}`; four nonempty strings identifying the selected, approved producer and data/rule interpretation. They must match the trusted build/profile configuration, not a caller-selected replacement. They do not themselves certify a build. |
| `basis` | Exactly `{plan_basis, input_basis, source_revision}`. The first two are nonempty strings; `source_revision` is a positive safe integer, excluding negative zero, matching the actual W6 repository revision from which the producer rendered. `plan_basis` equals the Start's existing `plan_basis`; `input_basis` is the **existing qualified producer's** authenticated input-basis identifier. No new digest formula, fake basis identifier or comparison of client/server revisions. The actual commit must also check the repository's retained token, not use this captured revision alone as a fence. The final integration must demonstrate the existing basis resolver/generation fence; this proposal does not settle the still-open normalizer/Q1/Q3 protocol. |
| `session` | Exactly `{instruction, reason, confidence}`; each is a cell below, recording the session-level material actually displayed. Missing historical evidence uses `unknown`, not a regenerated explanation. |
| `slots` | Nonempty ordered array of slot objects, exactly `{logical_set_slot, lift_lineage_id, label, load, reps, effort, setup, reason, confidence}`. Slot and lineage are nonempty strings; `logical_set_slot` is unique within this Start. Repeated lineage across different slots is valid. `label` is a nonempty literal display string, never identity. The other six fields are cells. Array order is original displayed order; do not sort by label, lineage, load or later performance. |
| cell | Exactly `{state, display, source_json}`. `state` is `specified`, `unknown` or `not_prescribed`; `display` is a nonempty literal string. For `specified`, `source_json` is a string containing the exact strict JSON encoding of the producer's corresponding resolved data value; for the other states it is `null`. Strict JSON must reject duplicate decoded keys, malformed UTF-8/BOM, nonfinite values and invalid syntax. Preserve that JSON string byte-for-byte, including key order, decimal spelling and escapes. It is evidence, **not** an automatically accepted engine operand. |

Cells deliberately preserve both the displayed instruction and its original typed representation. They do not invent a new load/effort calculus: numeric quantities, ranges, bodyweight/assistance, bounded effort and unknowns retain the producer's approved representation. `specified` is permitted only when that producer has actually resolved and qualified the representation; an unimplemented scalar-to-per-set mapping cannot be marked specified. Consumer renders `display` as text, never markup, and does not feed `source_json` to the progression engine without its separately qualified mapping. In particular, `at_least3` is not exact3 and missing effort is not zero. No new training rule or scientific confidence threshold is selected here.

Every instruction visible at Start must be represented at the correct session/slot level. A field absent from the display is `not_prescribed` only if the producer establishes that absence; inability to recover its past meaning is `unknown`. An unknown/not-prescribed cell's display explains that absence; it is not represented as literal past wording. The consumer cannot omit a known per-set load just because the legacy engine DTO contains a scalar. A `specified` cell's raw value and display must come from the same producer result; the producer-to-render-to-capture equality test is mandatory.

## 3. Producer, commit and retry

The host asks the qualified producer to render from one loaded, authenticated logical generation and accepted plan/rule basis. **Before the builder**, validate descriptors and recursively copy the closed JSON shape without invoking getters, then deep-freeze that private copy of the same displayed result. This is one testable precondition: reject cycles, accessors, undefined/nonfinite values and other §2 exclusions with the existing typed refusal; retain no caller-owned nested references; expose no arbitrary `extra` override. Test hostile getters (zero invocations), post-build caller mutation, reserved-field overrides, cycles and undefined/nonfinite transport mismatches. The actual builder alone does not provide these safeguards: it merges `extra` over core fields and retains nested references. Immediately before staging, compare the expected repository generation and producer/basis identity; any change requires re-render/revalidation under existing rules, not silently capturing different instructions. Current standing/integrity/negative/lease/write-failure precedence remains. This is not a new online requirement for an already valid offline Q3 capability.

The proposed public-client seam is `prepareWorkout({planned_split_slot_id}) -> {preparedId, view}` then `startPreparedWorkout({preparedId, effective}) -> existing durable command outcome`. `workoutProducer` is a trusted static, synchronous configuration dependency, not a callback supplied by either call. Preparation loads and verifies a real repository snapshot, invokes that producer on its qualified inputs, retains the exact capture plus snapshot revision/token and current context/observation epoch in a private instance-owned entry, and returns an opaque local handle. The renderer displays the retained capture's view. A caller cannot submit its own capture, source revision, producer identity or substitute basis through this API. The handle is neither an operation identity nor a remotely trusted capability; it does not survive client disposal/relaunch. Existing committed Starts supply resume history instead.

Starting resolves the handle in that same instance and constructs the trusted `workout` action from its retained copy; `effective` keeps its existing athlete-attested validation. The existing W6 `bridge.mjs:40–45` supplies and deep-freezes `snapshotRevision`, original command arguments, prepared batch and session/observation epochs for `validateCommit`, followed by `repository.commit(snapshot,...)` checking the actual token inside its transaction (`repository.mjs:129`). Its existing `bridge.mjs:30–37` also rejects `PREPARED_BATCH_MISMATCH` by comparing operation bytes. Extend that **existing** validator to require the privately retained prepared entry, matching source revision/basis/profile/context and exact captured Start in the batch; the submitted revision alone is never authoritative. Public captured-profile Start without a valid preparation handle refuses before acknowledgment. Normal set/skip/close commands remain their own operations. A stale preparation retains input and requires a fresh reviewable preparation under existing state3 unless a higher-priority standing/integrity condition applies; it never invents state17/18 merely because the plan changed.

One handle cannot issue concurrent duplicate Starts. Definite precommit failure may retry only while its source/context remains valid; confirmed commit binds it to the committed Start; uncertain commit locks it pending the existing persisted-operation reconciliation. An internal CAS retry must not replace its captured prescription with a newly generated one. Test disposal, caller mutation, context change and mutation between preparation/staging/final validation; a successful current-head proof alone cannot revive a consumed handle.

Extend the trusted workout command's Start input with this one field; expose no arbitrary `extra` override to UI callers. Prepare checks the closed capture shape, uniqueness/order, basis equality and trusted producer/generation relationship before the existing builder. Shared shape validates the additional field only for session-start in the selected amended profile. Current quantity/correction schemas are not silently broadened. Actual authority admission still authenticates identity/lease/schema, ownership and dependencies before acceptance; a forged capture profile or foreign basis must not grant rights. The existing semantic basis resolver must supply any operation references used by the basis and include them in the actual dependency/ownership checks; recording an opaque string alone does not satisfy that gate.

The same `commitBatch` writes the sealed Start operation, sequence/checkpoint and nonempty outbox in one candidate generation. W6 encrypts and commits that whole generation before acknowledging Saved. No separate local capture metadata is authoritative; an optional render cache is derived from the immutable Start and may be discarded/rebuilt. Abort, stale revision and uncertain commit retain the existing entered-value/recovery behavior. Dispose is not cancellation: after an uncertain Start, reconcile the actual stored operation before permitting another Start. Exact retry reuses the same already committed Start bytes, including capture; re-running the producer on retry is forbidden.

Keep declared transport limits: `/op` body262144 bytes and complete R1 proof1048576 bytes, including repeated retained operation/log encodings. Check full encoded request before local acknowledgment; no truncation or smaller hidden workout/history cap. Test actual largest supported prescriptions and imported histories in the full recovery envelope, not just capture size. If legitimate supported data cannot fit, the existing reviewed transport/resource decision is required; do not drop history or mark this representation release-ready. No resource acceptance follows from the small example below.

## 4. Authority, recovery and immutability

No `COLLECTIONS` or physical SQL migration change is needed **for inline representation**. The existing P1 `operations`/`log` value encryption covers the new field; original minimal SQL projections, storage stamp/control guard and signing/identity domains stay unchanged. Whole operation commitment binds the capture under the NFC equivalence contract above; independent tests must attack every slot field outside that equivalence, reorder slots and substitute another athlete/device/Start. Include an NFD/NFC same-commitment witness and separately prove exact original bytes through encryption/recovery. Authority signature verifies committed facts, not physiological validity.

Signed pull/snapshot/R1 recovery must preserve this exact Start and capture through authenticated same-athlete recovery on a different enrolled device. The recovered Start's original device and basis remain its origin; do not require the reading device to equal its origin. Validate capture semantics after authenticating raw bytes and the complete supported schema; a well-signed unknown profile is not permission to guess. Missing/tampered/unusable stored truth takes the existing integrity/recovery path18; independently known standing loss remains17. Unknown legacy capture is represented explicitly and cannot be silently manufactured from the current plan.

Absence of capture in a valid supported legacy Start is explicitly unknown historical prescription, not by itself state18. An absent mandatory field in an authenticated new captured-profile record is an integrity/schema failure; never silently reinterpret it as legacy. The capture is immutable. Set observations, skips, close, corrections and removal remain separate append-only facts; they cannot overwrite original instructions or completed values. Current safety is a separate evaluation which can MODIFY or refuse the currently permitted action while leaving historical display intact. Show the new instruction/reason separately. A current alarm may raise the effort floor, so “resume” never blindly executes the historical ladder. Close/reopen and another session's close must preserve the correct Start/slot identities and draft boundary.

Later-added slots/instructions still require the already-required explicit append-only workout contract; this initial-Start field cannot be rewritten to pretend they existed at Start. That existing join, full correction/partition/eligibility behavior and complete normal Finish remain required; this proposal does not replace them with a local-only feature or declare them deferred.
