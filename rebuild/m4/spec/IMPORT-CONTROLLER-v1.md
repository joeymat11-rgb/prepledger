## Implemented preparation

`rebuild/m4/import/prepare.cjs` is a Node-only, in-memory preparation adapter. Inject the actual installed engine and W6 `parseStrictJson`. It imports no engine entry point itself. Its synthetic test is local only and uses the installed engine; neither it nor the full seeded engine is a browser asset. No app/bundle allowlist changes are made.

`prepare(sourceBytes, {localBytes})` copies both byte buffers before parsing or engine calls. `localBytes` is optional for a source-only preview; a replacement/merge of an existing installation MUST supply the real independently captured local engine snapshot through the future qualified controller. Absence never means an existing account is empty. It returns isolated accessors for original bytes/states, candidate bytes/state and a frozen local summary. It makes no storage call and no promise that preparation survives a process exit.

The supported-version migration factory is reused, not copied. Current-schema migration calls the mutating `_settleExit`; earlier migration may return a different object. The adapter retains the actual return, uses separate working copies, performs the real merge/settle when local input is supplied, and runs actual `dataLossGuard` on independent copies of both original states. JSON output must round-trip without silent NaN/Infinity/undefined/hole/negative-zero conversion. Exceptions expose fixed codes rather than private engine prose or guard details.

Unsupported/future input is refused before any engine call. v1/v2 require a separately qualified seed-template/profile path; there is no implicit Joe or Dad default. v3 through the installed schema may enter the existing migration, but any migration/schema/serialization/guard failure refuses preparation. Focused execution covers v59 and v60; it does not qualify all historical private profiles. The underlying engine's required future-schema identity return remains unchanged.

The summary's source/candidate/local digests identify local bytes only. They are private once used with private data. Do not log, publish or treat them as signatures, source-generation IDs, accepted frontier receipts or consent. Historical `accepted`, `targets`, adjustments and other decision records remain verbatim in the original source. Reconciliation of those fields in the candidate does not grant current plan authority. `activation: pending` is a local disposition, not a new durable knowledge fence.

The guard is stronger than recordCounts but is not whole-value parity. Its D33 protections include record/date/exercise/occupied-set identity and correction coverage. A same-date measurement value change can pass it. A focused explicit scope test preserves this fact. Do not turn guard success into “every value preserved,” scientific acceptance or qualified carryover. Exact original bytes remain available for the required full port/parity review.

Include the independent pending operations/outbox; engine state alone cannot represent their custody. No local enumeration/sequence or cached view substitutes for authenticated source coverage.

Separate historical source decisions, derived candidate guidance, and authority-accepted current targets/consent. Give retries stable source identity from this custody layer; do not re-mint IDs or re-run writers to manufacture acceptance.
3. Before activation, verify the same source, account, checkpoint/frontier and current repository revision/token, plus the actual applicable issuer/permission/schema/clock/standing conditions. A changed source or intervening operation requires fresh preparation/reconciliation. The existing accepted wire contract must explicitly authorize and bind the activation; preparation supplies no fake `activation_op_id`, metadata token or alternate proof channel.
4. Publish the chosen source/checkpoint, accepted current-plan provenance and complete resulting projection atomically. Keep the earlier source and checkpoint. No success paint, current Start permission or import anchor before the actual accepted binding and durable publish. A crash must leave either the previous active state or the entire new state recoverable, never a mixed generation.
5. Rollback selects the prior projection checkpoint and replays the complete subsequent accepted log plus all local pending operations through the existing projectors, preserving identities/bytes/dispositions. It does not restore an old database over current facts. Imported originals remain retained. Repeated delivery or rollback must not execute a writer or consent transaction twice.

The exact issuer/authority representation, encrypted inactive-generation custody and activation/recovery encoding need a coherent amendment in the existing R1/W6 contract before their implementation can claim acceptance. In particular, the current closed operation registry and P1 coverage cannot be extended by placing extra keys in metadata. K1 baseline-only deletion/recovery and schema2 old-pending compatibility remain real prerequisites, not solved by this document.
