## Implemented preparation

`rebuild/m4/import/prepare.cjs` is a Node-only, in-memory preparation adapter. Inject the actual installed engine and W6 `parseStrictJson`. It imports no engine entry point itself. Its synthetic test is local only and uses the installed engine; neither it nor the full seeded engine is a browser asset. No app/bundle allowlist changes are made.

`prepare(sourceBytes, {localBytes})` copies both byte buffers before parsing or engine calls. `localBytes` is optional for a source-only preview; a replacement/merge of an existing installation MUST supply the real independently captured local engine snapshot through the future qualified controller. Absence never means an existing account is empty. It returns isolated accessors for original bytes/states, candidate bytes/state and a frozen local summary. It makes no storage call and no promise that preparation survives a process exit.

The supported-version migration factory is reused, not copied. Current-schema migration calls the mutating `_settleExit`; earlier migration may return a different object. The adapter retains the actual return, uses separate working copies, performs the real merge/settle when local input is supplied, and runs actual `dataLossGuard` on independent copies of both original states. JSON output must round-trip without silent NaN/Infinity/undefined/hole/negative-zero conversion. Exceptions expose fixed codes rather than private engine prose or guard details.

Unsupported/future input is refused before any engine call. v1/v2 require a separately qualified seed-template/profile path; there is no implicit Joe or Dad default. v3 through the installed schema may enter the existing migration, but any migration/schema/serialization/guard failure refuses preparation. Focused execution covers v59 and v60; it does not qualify all historical private profiles. The underlying engine's required future-schema identity return remains unchanged.

The summary's source/candidate/local digests identify local bytes only. They are private once used with private data. Do not log, publish or treat them as signatures, source-generation IDs, accepted frontier receipts or consent. Historical `accepted`, `targets`, adjustments and other decision records remain verbatim in the original source. Reconciliation of those fields in the candidate does not grant current plan authority. `activation: pending` is a local disposition, not a new durable knowledge fence.

The guard is stronger than recordCounts but is not whole-value parity. Its D33 protections include record/date/exercise/occupied-set identity and correction coverage. A same-date measurement value change can pass it. A focused explicit scope test preserves this fact. Do not turn guard success into “every value preserved,” scientific acceptance or qualified carryover. Exact original bytes remain available for the required full port/parity review.

### Named custody and recovery amendment — proposed implementation constraints

APM's bounded read-only review of a60f5a2 found no preparation defect in its reviewed scope and identified the actual repository constraint: `readRecords` reads only active/previous; `publish` overwrites previous on EVERY commit. Therefore that rotating slot is not the import rollback checkpoint. Two ordinary saves after activation would otherwise erase the selected pre-activation baseline. This is a controller dependency, not a new engine defect or independent acceptance receipt.

The controller must retain an immutable, named custody record independently of active/previous, using the existing encrypted repository/storage boundaries. Its required contents are the exact selected source bytes and candidate bytes, their local identifiers/digests and migration/build context, the complete pre-activation projection checkpoint, accepted frontier/prefix identity, and every pending operation/outbox identity and exact stored body at that checkpoint. The source and checkpoint record must remain readable after later commits and repeated rollback. A local name or digest does not confer authority; the signed activation must bind that retained identity and the actual checked account/source frontier.

Reconciliation, encrypted export and isolated restore must cover the source record, named checkpoint, pending work and signed activation binding together. At present R1 `project.cjs` enumerates exactly20 collections, enforces exact metadata/state fields, and `storage/row-codec.cjs` restricts sealing to that inventory. `VERIFIED_IMPORT` in accountRegistry only describes retained authority-history origin; it is not an implemented legacy-engine importer or a source/checkpoint receipt. Consequently, neither an extra metadata key nor changing that label supplies custody/recovery coverage. Any new retained representation must be added coherently to the existing versioned inventory, sealing, signed coverage and client verification; old pending operations/replay remain valid under their original profile.

Final local activation reuses the existing revision/token-guarded atomic `repository.commit`; a separate store or parallel authority is unnecessary. The import extension must validate the named record and actual signed binding against the same active revision/context immediately before that commit. On recovery, a missing named record or source binding remains unresolved integrity; do not silently activate cached guidance or reinterpret a remaining marker as proof. This amendment defines required custody contents and transaction behavior, not a new accepted wire operation name.

The first full vertical case is staged import → genuinely accepted activation → a later remote accepted fact and a local pending fact → at least two later durable commits → rollback → close/reopen. Assert every original source byte, prior and current capture, later accepted fact, pending operation body/identity, and truthful disposition remains available. Repeat rollback and delivery; no duplicate writer effect or deleted imported record. Exercise interruption before and after publication. This case must run through actual authority/HTTP and repository implementations when their contract extension exists; the preparation tests do not stand in for it.

### Implemented local custody at W6 0b281870fa6ed51686257afa70f738be704b4902

`rebuild/m3/w6/import-custody.mjs`, exposed through `repository.importCustody({parseStrictJson,validateContext})`, stores named inactive records in the existing generations object store, independently of active/previous. `stage(id, expected, {sourceBytes,candidateBytes,localBytes,engineContextJson})` captures input before asynchronous work and reads the checkpoint from the actual encrypted active generation. The local-only encryption domain is earned/local-import-custody/v1 with AES-GCM additional data binding profile, namespace and source name. This differs from the active-generation format and cannot be promoted to active by moving the record. Atomic staging compares the active revision AND token in its final transaction and checks current context there. It publishes no active generation. This API preserves bytes, not provenance acceptance. The migration context is supplied and unverified, the source name is a local custody identifier, and all results say activation pending. There is no rollback or activate method and no automatic active-state restore.
