## Later-added slots: proposed durable representation

The initial Start.prescription_capture cannot be changed or padded to claim extra slots existed at Start. Merely naming a new logical_set_slot in a Set currently fails actual W6 continuation and M4 layout mapping. Recording an unperformed extra slot as a zero-rep Set would be false data.

Propose a NEW version2-only operation kind `session-extension`, class session, with envelope `session_start_op_id` and payload containing an immutable extension capture. This is an explicit addition to the16 existing A3 kinds, requiring affected technical acceptance and a version-specific builder/admission amendment; it cannot be smuggled through legacy lineage/fact/Set or enabled by changing the global v1 kind list. Original version1 validation stays exact.

The extension capture binds the original Start, the actual retained current source/basis and exact displayed additional instruction cells with the same producer/cell discipline as CAPTURE-START. Each added slot's identity is a canonical tuple derived from the extension operation's immutable ID and its within-extension index; the trusted command allocates it before the ONE original operation commitment. It is not a regenerated count-based ID on reload or retry. Each added slot names its actual lift lineage. The extension's row and every later Set/Skip must declare actual reference/ownership coverage. Existing captured slots remain in place; additions form a separate explicit sequence after their lift's captured slots, ordered from the complete accepted causal/athlete-log sequence. Concurrent additions remain distinct, never deduplicated by position or label. Pending additions retain their own identities and explicit causal order; no device sequence becomes a fabricated accepted tie-break.

A normal Set/Skip for an added slot carries an explicit `slot_definition_op_id` referring to the extension in addition to its Start/lineage/logical slot. The full validator verifies that exact declared slot exists in that immutable extension and belongs to the same Start/lift. Original captured slots have no extension reference. Unknown definitions WAIT at admission; locally unknown definitions cannot be acknowledged. Removing/correcting an observation preserves its slot definition and original instructions. An extension's original capture remains immutable; removal/correction of definitions and cross-device ordering must be reconciled with the existing edit/partition contract before final schema freeze.

An athlete-requested extra set and an engine-prescribed increase are different records of authority. The former may explicitly have not_prescribed load/reps/effort cells when the displayed action supplies no machine target, retaining the athlete's actual choice. It does not alter accepted plan set count or imply that the engine recommended extra volume. Any displayed machine target requires the actual qualified producer/current safety and explicit session-choice basis. Existing captured targets are never silently recalculated by extending the workout. Subsequent history and the next prescription must consume the complete added-slot/performed record with appropriate completion, comparability and confidence rules; unsupported numeric/configured mixtures cannot be collapsed to a scalar or silently discarded.
