(6) LAWS / SUITE LIBRARY I BELIEVE ARE WRONG (not edited)
  a. lib/canonical.cjs decimal(): (i) |n| ≥ 1e21 is emitted in exponent form ("1e+21") because Number.prototype.toFixed returns
     ToString for such magnitudes — contradicting sheet line 100 ("decimal representation"), the law's own comment ("canonical decimal,
     never '1e+21'") and brief §3; (ii) the trailing-zero strip is applied to that exponent form, so 1.5e30 and 1.5e300 BOTH encode as
     "1.5e+3" — two values, one commitment; (iii) |n| < 1e-6 is rounded to 20 fractional places, so 1e-21 → "0" (collides with 0) and
     -1e-21 → "-0" while -0 → "0". Law B-A1-canonical-v1 binds the candidate to these bytes through fixture e1 (1e21), so the product
     reproduces the profile (documented in canonical.cjs). Fix needs a canonical-v2 profile in lib + the law (A1 says the encoding is
     versioned, so this is an encoding-version bump, not a silent edit).
  b. lib/canonical.cjs sorts map keys by UTF-16 code units (JS default sort), not code points as brief §3 says (U+1F600 sorts before
     U+FF01); map keys are not NFC-normalized (values are). The product matches the suite; the brief's wording is the inaccurate side.
  c. B-state-5 asserts the literal frontier numbers "W1"/"W2" while its inputs (planHistory transactions) carry no frontier; any product
     must invent them (seam 5j). The law should either supply applied_at_w in the fixture or assert the shape, not the numbers.
  d. B-durability's exact outbox count (7 for 7 actions) makes a lazily-created session-start operation for LOG SET impossible (seam 5f);
     the sheet's A3 rule "every set targets an immutable session-start identity" then has to be met by an explicit start action.
  e. reference/client.cjs (model only, not a law): candidateEdge accepts the 23:00→01:00 skew envelope in either date direction; a
     single session start yields an ambiguity component of one and governing state 14. The laws pass with the strict rules too.
